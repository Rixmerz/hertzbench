The radio network between your boards, simulated.

Run N microcontroller boards on real firmware and let them talk over simulated wireless links with a distance, a path loss, a latency and a loss. Local, free, open source under AGPLv3.

What it is

  • Links with a channel model

    Each Wi-Fi/IP and ESP-NOW frame pays for the distance. The engine computes RSSI and SNR from the positions and any walls, picks a rate, rolls retries and loss, and delivers the frame after the modelled delay, jitter included. Its randomness comes from the scenario seed, so the same frames on a link get the same outcomes.

  • Real firmware

    ESP32 boards run under QEMU with their own MAC addresses. Scripted boards, a traffic generator instead of firmware, run with nothing but Deno.

  • Five kinds of link

    Wi-Fi/IP, ESP-NOW, LoRa (SX127x) and nRF24L01+ chip models at their SPI interface, and BLE through a virtual controller on an HCI UART, with the firmware built host-only for it. LoRa, nRF24 and BLE share a chip-level air where overlapping packets can collide. Every report prints the fidelity of each part.

  • An MCP server for AI agents

    hertzbench mcp gives an agent tools to build, edit, run and steer scenarios: move a node, force loss or latency, raise the interference on a link, and read the serial output and the metrics while the run plays.

  • A live view

    hertzbench view draws the nodes on a map, colors each link by signal or by loss, and lets you drag a node to move it mid-run. It is optional and needs no build step.

  • A mobile bridge

    Lets a real phone on the same Wi-Fi reach a simulated board over IP, with mDNS, or over BLE through BlueZ on Linux. It has not been tried with a real phone yet.

  • Plain outputs

    A scenario is a YAML file. A run writes metrics.json, air.pcap for Wireshark and events.jsonl, and exits non-zero when an assertion fails.

Install and first run

These commands run Hertzbench from source with Deno 2.x (other ways to install Deno). They use scripted boards, so no QEMU is needed. The run lasts 6 s of engine time, prints per-link RSSI, loss and latency, and writes metrics.json, air.pcap and events.jsonl.

Linux 
# Install Deno, then fetch Hertzbench
curl -fsSL https://deno.land/install.sh | sh
git clone https://github.com/Rixmerz/hertzbench.git
cd hertzbench/hertzbench

# Three scripted boards; one walks behind a wall
deno task hertzbench run scenarios/examples/udp-3-scripted.yaml --out /tmp/hzb-out

# Watch it live, then open the address it prints
deno task hertzbench view scenarios/examples/live-3-scripted.yaml --out /tmp/hzb-view

# Put hertzbench and hzb on your PATH, then connect Claude Code (MCP)
deno task install-cli
claude mcp add hertzbench -- hertzbench mcp --workspace /path/to/your/project

ESP32 boards on real firmware need a libqemu built from the public QEMU fork and an Arduino or ESP-IDF toolchain; the steps are in the ESP32 guide. Windows and macOS have not been tried, see Status.

Status, as tested

The ESP32 runs below were done on Linux x86_64. No Windows or macOS run is recorded, so treat both as untested. The ESP32 results are from 2026-10-23, on a libqemu built from the public lcgamboa fork without root or Docker.

  • RF engine, adapters, CLI and outputs

    Tested

    Channel model, medium, seeded RNG, event log, metrics.json, air.pcap and assertions are unit-tested on a manual clock and through the real CLI.

  • ESP32 over Wi-Fi/IP, LoRa and BLE on real firmware

    Passes

    Three boards exchange UDP; behind the wall one link loses frames and the other holds. The LoRa gateway scenario (arduino-LoRa on an SX1276 model) and the BLE scenario pass their assertions. The BLE firmware is a host-only Bluedroid build (ESP-IDF v5.3.6), so its binary differs from production.

  • ESP-NOW on real firmware

    Fails

    4 of 7 assertions pass. The boards boot with their own MACs and broadcasts arrive, but the gateway stops taking frames after 21, when the QEMU fork's 20-frame injection queue overflows, and every sensor reports its sends as failed. ESP-NOW is tested with scripted boards.

  • MCP server and live view

    Partly

    Tested through the real hertzbench mcp process and in headless Chromium, with scripted boards. ESP32 boards through MCP or the view have not been run.

  • Mobile bridge

    Partly

    On real firmware the IP bridge serves an ESP32's web server to the host's curl, and BlueZ advertises the firmware's GATT service. No phone has been used, and mDNS has not been seen from another host. The BLE bridge needs Linux with BlueZ.

  • nRF24L01+

    Partly

    The chip model is done and tested. No example runs it on an ESP32 board.

  • Docker Compose file

    Not started

    There is no docker-compose.hertzbench.yml yet.

  • Limits of the channel model

    Limits

    On Wi-Fi/IP and ESP-NOW there are no collisions, carrier-sense contention, hidden nodes or capture effect (each link is simulated alone), and no adjacent-channel interference. LoRa, nRF24 and BLE do model collisions on the chip-level air, but a scenario runs one PHY, so BLE and Wi-Fi interference is not modelled. ESP32 boards run on wall-clock time, so latency is modelled by the engine, not measured on the board. Fidelity notes.
