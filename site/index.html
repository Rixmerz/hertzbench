What Hertzbench adds to Velxio

Velxio emulates a circuit. Hertzbench adds the air between boards.

Velxio emulates one circuit: a board's CPU (AVR, RP2040, ESP32 under QEMU), its components and the wires between pins, on an interactive canvas, with one virtual access point that NATs to the internet. Hertzbench keeps all of that as it is and adds a network: N boards, each at a position in metres, talking over simulated radio links. It patches one Velxio code file, esp32_worker.py (the board's network device and a link from its SPI bus to a radio chip model); MCP, ESP-NOW, BLE, the mobile bridge and the view touch none.

How it works

One file in, one verdict out.

Everything below is from the same run as the screenshot above, five ESP32 boards running the ESP-NOW sketches in scenarios/examples/fw/.

  1. A scenario file

    Nodes, positions in metres, walls, the radio of each node and what must hold at the end.

  2. Emulated boards

    Each ESP32 runs its own firmware under QEMU, with its own MAC. Serial output is kept per board.

  3. Simulated radio links

    Every frame pays for the distance and the wall: RSSI, SNR, rate, retries, loss and delay.

  4. A result you can assert on

    The run exits non-zero when an assertion fails, and leaves metrics.json, air.pcap and events.jsonl.

Features

Every part it adds, each with its proof.

Fidelity levels are the ones every report prints: F1 and F2 mean the same firmware binary; F3 means a host-only build. A scripted board is a traffic generator, not firmware, and the page says so wherever one is shown. Snippets without a date were run for this page on 2026-10-24 with scripted boards.

RF engine

Channel model v1

A separate Deno process carries every frame between boards. For each frame and each receiver it computes RSSI and SNR from the positions and the walls crossed, picks a rate, rolls the retries and the loss, and delivers the frame after the modelled delay, with jitter that grows with distance. Presets: free_space, indoor_office, urban, rural. Each frame draws from its own random stream named by the seed, the link and the frame's number on it, so outcomes do not depend on how links interleave.

qemu-wifi-l2 adapter

F2, same firmware binary

In Velxio each ESP32 has its own SLIRP network: boards cannot hear each other. The adapter gives each board's QEMU network device a socket to the engine instead, reads its Ethernet frames and writes the engine's deliveries back. The engine is a layer-2 switch with a virtual gateway at 192.168.4.1 that answers ARP and DHCP with a static lease per board. ESP-NOW rides on the same socket. One board can keep SLIRP for the internet (internet_gateway: true), off the medium.

Boards on a map

esp32 or scripted

A scenario places 2 to 10 boards at positions in metres. An esp32 board runs real firmware under QEMU, compiled from a sketch directory or given as a .bin, with its own MAC (02:68:7a:62:01:NN, in file order) and address (.11, .12, ...), and its serial output kept per board. A scripted board needs only Deno: it plays DHCP, pings, ESP-NOW or the host side of a LoRa, nRF24 or BLE sketch, so everything runs on a host without QEMU. count: 4 with a grid expands one entry into four boards. The ESP32-C3 and S3 are refused, with the reason.

YAML scenarios

One file per experiment

A scenario declares the environment and its walls, the nodes and their radios, per-link overrides (forced loss, extra latency, jitter, interference), a timeline of moves and link changes with labelled phases, the assertions, and an optional mobile bridge. Unknown fields are errors, durations need a unit, and every error names its field (nodes[1].position: expected [x, y] or [x, y, z]).

Wi-Fi/IP

F2, same firmware binary

Each board's Wi-Fi NIC is a QEMU network device on the engine instead of SLIRP. The engine is a layer-2 switch with a virtual gateway at 192.168.4.1 that answers ARP and DHCP. Three boards exchange UDP; behind the wall one link loses frames and the other holds.

ESP-NOW

F1, same firmware binary

The QEMU fork's Wi-Fi MAC turns each 802.11 action frame into pseudo-Ethernet and the engine carries it, with the fork's 10 ms ACK wait. The report lists every send as the sender's firmware sees it, and air-80211.pcap holds the frames as 802.11 for Wireshark. It needs a small patch to the fork's Wi-Fi MAC.

LoRa

F1, same firmware binary

The SX127x is modelled at its SPI interface, so arduino-LoRa runs on an SX1276 model with the same firmware binary. A gateway and six nodes 300 m apart, out to 1.8 km, at SF7 BW125: the link budget runs out along the line. LoRa, nRF24 and BLE share a chip-level air where overlapping packets can collide.

nRF24L01+

F1, chip model

The chip model is done and tested at its SPI command interface. No example runs it on an ESP32 board yet, so this run uses scripted hosts: one node 5 m from the gateway, one 400 m away. The scenario below is the one in hertzbench/tests/cli_test.ts; save it as nrf24.yaml to run it.

Scripted boards replay what a sketch would do; this shows the chip model and the channel, not firmware.

BLE

F3, host-only build

The firmware runs its real Bluedroid host stack, built host-only, and sends HCI over a UART. The board relays that UART to a virtual link-layer controller on the engine's air. The binary differs from production by that build option and the UART driver. The report lists every connection and disconnection and the ACL data, and hci-<node>.btsnoop opens in Wireshark.

Mobile bridge

Not a board

A real phone on the same Wi-Fi reaches a simulated board over IP, with mDNS, or over BLE through BlueZ on Linux. Every connection to the host's port becomes the bridge's own TCP connection to the node, so it pays the channel model from the bridge's position. Below, a scripted web node answers curl through the bridge on the host's port 8080.

Over BLE the bridge's node is a central on the simulated air: it connects to a peripheral, discovers its GATT server, and hands that table to BlueZ, which advertises it on the host's adapter. Each read, write and subscription a phone makes is replayed as ATT over the simulated connection, so a phone that walks away in the timeline loses the link.

On real firmware (2026-10-23) the IP bridge serves an ESP32's WebServer to the host's curl, and the BLE bridge mirrors the firmware's GATT while BlueZ advertises hzb sensor on hci0. No phone has been used yet, and mDNS has not been seen from another host.

MCP server

23 tools

hertzbench mcp gives an AI agent such as Claude Code tools to build, edit, run and steer scenarios while a run plays: move a node, force loss or latency, raise the interference on a link, read the serial output and the metrics. Every file it writes stays inside its workspace.

Tested through the real hertzbench mcp process with scripted boards. ESP32 boards through MCP have not been run.

Live view

Optional, no build step

hertzbench view draws the nodes on a map, colors each link by its signal or by its loss over the last 2 s, and plots every frame on a timeline: a mark per frame delivered or lost, and a vertical mark for every move and forced fault. Drag a node, or focus it and use the arrow keys, to move it while the run plays: the move goes through the same move_node tool an agent uses. It follows your light or dark setting, needs no build step, and reuses Velxio's design tokens, fonts and ESP32 DevKit drawing read-only.

CLI and assertions

hertzbench, or hzb

Four commands. run plays a scenario headless, prints the report, writes metrics.json, air.pcap (open it in Wireshark), events.jsonl and a serial log per board, and ends with RESULT: PASS or RESULT: FAIL. Assertions check a board's serial output within a time, or a link's metrics in a phase. Exit status: 0 passed, 1 an assertion failed, 2 an invalid scenario or a host that cannot run it, 130 interrupted (boards are stopped first), so a CI job can gate on it.

Install

Install and first run.

These commands run Hertzbench from source with Deno 2.x (other ways to install Deno). They use scripted boards, so no QEMU is needed. The run lasts 6 s of engine time, prints per-link RSSI, loss and latency, and writes metrics.json, air.pcap and events.jsonl.

Linux 
# Install Deno, then fetch Hertzbench
curl -fsSL https://deno.land/install.sh | sh
git clone https://github.com/Rixmerz/hertzbench.git
cd hertzbench/hertzbench

# Three scripted boards; one walks behind a wall
deno task hertzbench run scenarios/examples/udp-3-scripted.yaml --out /tmp/hzb-out

# Watch it live, then open the address it prints
deno task hertzbench view scenarios/examples/live-3-scripted.yaml --out /tmp/hzb-view

# Put hertzbench and hzb on your PATH, then connect Claude Code (MCP)
deno task install-cli
claude mcp add hertzbench -- hertzbench mcp --workspace /path/to/your/project

Status

What was run, and what was not.

The ESP32 runs below were done on Linux x86_64, with a libqemu built from the public lcgamboa fork without root or Docker. The screenshots on this page come from the same host.

  • RF engine, adapters, CLI and outputs

    Tested

    Channel model, medium, seeded RNG, event log, metrics.json, air.pcap and assertions are unit-tested on a manual clock and through the real CLI.

  • ESP32 over Wi-Fi/IP, ESP-NOW, LoRa and BLE on real firmware

    Passes

    Three boards exchange UDP; behind the wall one link loses frames and the other holds. The five-board ESP-NOW mesh passes 7 of 7 assertions (2026-10-24) with a small patch to the QEMU fork's Wi-Fi MAC. The LoRa gateway scenario (arduino-LoRa on an SX1276 model) and the BLE scenario pass their assertions. The BLE firmware is a host-only Bluedroid build (ESP-IDF v5.3.6), so its binary differs from production.

  • MCP server and live view

    Partly

    Tested through the real hertzbench mcp process and in headless Chromium, with scripted boards. ESP32 boards through MCP have not been run.

  • Mobile bridge

    Partly

    On real firmware the IP bridge serves an ESP32's web server to the host's curl, and BlueZ advertises the firmware's GATT service. No phone has been used, and mDNS has not been seen from another host. The BLE bridge needs Linux with BlueZ.

  • nRF24L01+

    Partly

    The chip model is done and tested. No example runs it on an ESP32 board.

  • Release binaries

    Partly

    The workflow and the six targets are in place, and a Linux x64 binary built by hand runs a scenario. No v* tag has been pushed, so nothing is published yet.

  • Docker Compose file

    Not started

    There is no docker-compose.hertzbench.yml yet.

  • Limits of the channel model

    Limits

    On Wi-Fi/IP and ESP-NOW there are no collisions, carrier-sense contention, hidden nodes or capture effect (each link is simulated alone), and no adjacent-channel interference. LoRa, nRF24 and BLE do model collisions on the chip-level air, but a scenario runs one PHY, so BLE and Wi-Fi interference is not modelled. ESP32 boards run on wall-clock time, so latency is modelled by the engine, not measured on the board. Fidelity notes.
